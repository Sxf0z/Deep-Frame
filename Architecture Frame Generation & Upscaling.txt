Architecture Technique Exhaustive : Développement d'un Utilitaire de Frame Generation et d'Upscaling Temps Réel
L'ingénierie d'un utilitaire d'upscaling spatial et de génération de trames (Frame Generation) fonctionnant en temps réel sous Windows, agissant comme un concurrent direct et strictement supérieur à des solutions telles que "Lossless Scaling", exige une maîtrise absolue des API graphiques bas niveau (DirectX 11/12, Vulkan) et de l'ordonnancement système. L'objectif architectural fondamental est d'atteindre une latence système quasi nulle, une empreinte mémoire (VRAM) marginale, et un coût de traitement (CPU/GPU) extrêmement faible permettant une exécution en moins de 2 millisecondes par trame générée.1
L'architecture conceptuelle s'inspire d'implémentations open-source modernes et sans injection (anti-cheat safe) telles que NovaScale-Upscaler 2, tout en introduisant des techniques d'estimation de mouvement par flux optique (Optical Flow) basées sur des shaders de calcul (Compute Shaders) et des primitives matérielles (msad4). Le présent document définit de manière exhaustive l'ensemble des composants nécessaires à la réalisation de ce projet, de la capture d'écran Zero-Copy à la boucle de synchronisation (Frame Pacing) haute résolution.
La Structure Parfaite du Projet (Dossier de Connaissances)
Pour assurer une scalabilité optimale du code, prévenir la dette technique et permettre une intégration fluide avec des agents d'intelligence artificielle spécialisés via le Model Context Protocol (MCP), l'architecture du projet doit être modélisée de manière rigoureuse. Le référentiel de connaissances se structure autour d'un répertoire docs/ contenant les spécifications techniques de chaque module. Cette structure n'est pas qu'une simple convention de nommage ; elle constitue le contexte persistant que l'environnement de développement utilisera pour contraindre la génération de code.
Le projet doit être divisé en cinq piliers fondamentaux :
1. docs/01_architecture_capture.md : Les méthodes DXGI et la gestion du Zero-Copy.
2. docs/02_compute_shaders.md : Le code HLSL/GLSL pour l'upscaler.
3. docs/03_optical_flow_fg.md : La logique mathématique de l'interpolation des frames.
4. docs/04_memory_management.md : Les règles strictes pour ne jamais surcharger la VRAM.
5. docs/05_ui_and_overlay.md : Comment faire flotter la fenêtre de manière transparente.
Les sections suivantes de ce rapport déclinent le contenu technique exhaustif qui doit figurer dans ces documents d'architecture, rédigés spécifiquement pour guider le développement bas niveau en C++ et Rust.
Capture et Affichage : Les Méthodes DXGI et la Gestion du Zero-Copy (docs/01_architecture_capture.md)
Le goulot d'étranglement majeur et historique des utilitaires de superposition vidéo réside dans le transfert des trames capturées de la mémoire vidéo (VRAM) vers la mémoire système (RAM) via le bus PCIe, suivi de leur ré-téléchargement vers le GPU pour traitement. Ce va-et-vient consomme une bande passante massive, induit une latence asynchrone inacceptable pour le jeu compétitif, et provoque une contention sur le bus système. L'architecture "Zero-Copy" garantit que la texture capturée ne quitte jamais, à aucun moment de son cycle de vie, l'espace mémoire du processeur graphique.

	L'API DXGI Desktop Duplication (IDXGIOutputDuplication) a longtemps été le standard industriel pour la capture à haute fréquence.5 Cependant, elle présente des défauts architecturaux rédhibitoires pour un utilitaire moderne : elle capture l'intégralité du bureau de composition, nécessitant une passe de shader supplémentaire pour rogner (crop) les coordonnées correspondant à la fenêtre du jeu ciblé.6 De plus, elle entre souvent en conflit de verrouillage exclusif (Exclusive Lock) lorsque les jeux utilisent le mode "Fullscreen Exclusive", provoquant des écrans noirs ou des échecs d'initialisation.6
L'API Windows Graphics Capture (WGC), introduite dans les versions modernes de Windows 10 et encapsulée dans le namespace WinRT Windows.Graphics.Capture, représente la solution architecturale définitive.7 WGC s'interface directement avec le Desktop Window Manager (DWM) de Windows, permettant de capturer des fenêtres spécifiques de manière isolée, même si elles sont partiellement masquées par d'autres éléments de l'interface utilisateur. Le filtre de composition du DWM redirige la chaîne de permutation (Swapchain) du jeu directement vers un pool de frames alloué par l'application hôte.
Implémentation du Zero-Copy via WGC et Direct3D 11
Le cœur de la capture WGC repose sur l'instanciation de la classe Direct3D11CaptureFramePool. Cet objet permet de pré-allouer un ensemble de buffers circulaires (trames) directement dans la mémoire de l'adaptateur graphique.8 Pour obtenir des performances maximales et déjouer la synchronisation forcée avec la pompe à messages du thread principal (UI Thread), il est impératif d'utiliser la méthode CreateFreeThreaded.9 Cette méthode détache la réception des événements FrameArrived vers un thread de travail (Worker Thread) interne, annulant l'attente liée à la boucle de messages Win32.
Le défi technique de WGC en C++ réside dans le pont (Interop) entre le monde COM/WinRT (qui retourne un objet abstrait IDirect3DSurface) et le monde DirectX 11 natif (qui nécessite un pointeur ID3D11Texture2D pour lier la ressource aux shaders). La documentation standard omet souvent cette étape cruciale, conduisant les développeurs à utiliser des fonctions de copie logicielle. Le secret du Zero-Copy réside dans l'utilisation de l'interface non documentée publiquement mais standardisée IDirect3DDxgiInterfaceAccess.8
L'architecture C++ pour l'extraction Zero-Copy s'articule comme suit :






C++
// Inclusion des headers d'interopérabilité WinRT/DirectX nécessaires
#include <windows.graphics.capture.interop.h>
#include <windows.graphics.directx.direct3d11.interop.h>
#include <winrt/Windows.Graphics.DirectX.Direct3D11.h>

// Définition de l'interface d'accès DXGI (GUID spécifique)
struct __declspec(uuid("A9B3D012-3DF2-4EE3-B8D1-8695F457D3C1")) 
IDirect3DDxgiInterfaceAccess : public IUnknown {
   virtual HRESULT STDMETHODCALLTYPE GetInterface(REFIID iid, void** p) = 0;
};

// Fonction critique de récupération de la texture VRAM sans copie
winrt::com_ptr<ID3D11Texture2D> ExtractTextureZeroCopy(
   winrt::Windows::Graphics::DirectX::Direct3D11::IDirect3DSurface const& surface) 
{
   // Casting de la surface WinRT vers l'interface d'accès bas niveau
   winrt::com_ptr<IDirect3DDxgiInterfaceAccess> dxgiInterfaceAccess = 
       surface.as<IDirect3DDxgiInterfaceAccess>();
   
   winrt::com_ptr<ID3D11Texture2D> nativeTexture;
   
   // Extraction directe du pointeur ID3D11Texture2D sous-jacent
   HRESULT hr = dxgiInterfaceAccess->GetInterface(
       __uuidof(ID3D11Texture2D), 
       nativeTexture.put_void()
   );
   
   if (SUCCEEDED(hr)) {
       return nativeTexture; 
   }
   return nullptr;
}

Une fois le pointeur ID3D11Texture2D récupéré, il possède nativement les attributs D3D11_BIND_SHADER_RESOURCE.13 Cela signifie qu'une Shader Resource View (SRV) peut être créée immédiatement par-dessus cette texture. Le GPU peut alors lire directement la texture capturée depuis les registres des Compute Shaders, annulant totalement le surcoût de capture. Dans un environnement Rust utilisant la crate windows-rs, la logique est identique via les appels GetInterface::<ID3D11Texture2D>() après avoir obtenu le Direct3D11CaptureFrame.13
Algorithmes d'Upscaling Ultra-Légers (docs/02_compute_shaders.md)
Les algorithmes basés sur l'intelligence artificielle (comme DLSS ou les itérations avancées de XeSS) requièrent la présence de matériel dédié tel que les Tensor Cores ou les matrices XMX, ou imposent une charge de calcul mathématique (ALU) et une consommation de bande passante VRAM incompatibles avec un utilitaire générique.15 L'objectif étant de maintenir une charge GPU globale inférieure à 5% sur une machine de milieu de gamme (type Asus TUF Dash F15), l'architecture doit s'appuyer exclusivement sur des algorithmes spatiaux déterministes, implémentés via des Compute Shaders.

	La solution la plus élégante et performante pour concurrencer les outils commerciaux est une implémentation optimisée et combinée d'AMD FidelityFX Super Resolution 1 (FSR 1).1 Contrairement à ce que son nom suggère, FSR 1 n'est pas lié au matériel AMD et s'exécute sur n'importe quel GPU compatible DirectX 11 via HLSL.16 L'algorithme se décompose intrinsèquement en deux passes distinctes : Edge Adaptive Spatial Upsampling (EASU), qui effectue la mise à l'échelle en détectant et en préservant les gradients directionnels, suivi de Robust Contrast Adaptive Sharpening (RCAS), qui restaure la netteté perdue lors de l'interpolation sans brûler les contrastes.18
Optimisation Extrême : La Fusion Single-Pass EASU et RCAS
Dans l'implémentation de référence AMD, EASU écrit son résultat dans une texture intermédiaire en mémoire globale (VRAM), qui est ensuite lue par la passe RCAS.18 Ce changement de contexte (Context Switching) et cette barrière de synchronisation mémoire constituent une perte de temps GPU inacceptable pour un budget de 2 ms.
L'architecture proposée fusionne ces deux passes en un unique Compute Shader.19 Les pixels interpolés par l'algorithme EASU sont conservés dans les registres vectoriels locaux (SRAM) de l'Unité de Calcul Mathématique (ALU), puis immédiatement traités par la logique mathématique RCAS avant d'être écrits une seule fois vers la cible de rendu finale (UAV). Cette approche "Single-Pass" réduit la bande passante mémoire requise de 50% et abaisse le temps d'exécution sous la barre des 0.4 millisecondes sur des architectures de type NVIDIA Pascal (GTX 1060) ou ultérieures.2
Le concept architectural en HLSL s'exprime par le contrôle précis des groupes de threads pour maximiser le taux d'occupation (Occupancy) des processeurs de flux :






High-level shader language
// Définition de la taille du groupe de travail (Wavefront/Warp friendly)
[numthreads(64, 1, 1)]
void CS_UpscaleMain(uint3 LocalThreadId : SV_GroupThreadID, uint3 WorkGroupId : SV_GroupID) 
{
   // Calcul de la coordonnée de la texture de destination
   uint2 targetCoord = uint2(WorkGroupId.x * 64 + LocalThreadId.x, WorkGroupId.y);
   
   // Normalisation des coordonnées spatiales
   float2 texCoords = (float2(targetCoord) + 0.5f) * InvOutputResolution;
   
   // 1. Passe EASU : Échantillonnage adaptatif des contours
   // Utilisation de Gather4 pour récupérer 4 texels adjacents en une seule instruction mémoire
   float3 easuColor = ComputeEASU(texCoords, InputTexture, LinearSampler);
   
   // 2. Passe RCAS intégrée : Amélioration du contraste locale
   // Exécutée immédiatement en registre. Aucune lecture VRAM supplémentaire n'est requise.
   float3 finalColor = ComputeRCAS(easuColor, targetCoord);
   
   // 3. Écriture directe et unique vers la ressource cible (UAV)
   OutputUAV[targetCoord] = float4(finalColor, 1.0f);
}

L'utilisation de la directive CS_5_0 ou supérieure en HLSL garantit la prise en charge des instructions Gather4. Si le compilateur DirectX 12 Agility SDK est utilisé, le Shader Model 6.2 (CS_6_2) permet d'exploiter des opérations de niveau "Wave" (Wave Intrinsics) telles que WaveActiveSum, autorisant la coopération entre les threads d'un même groupe sans recourir à la mémoire partagée (groupshared) fortement latente.16
Frame Generation : Motion Vectors et Flux Optique (docs/03_optical_flow_fg.md)
Générer une trame intermédiaire temporelle (Frame   ) de haute qualité visuelle en respectant un budget d'exécution total (Upscaling + Frame Gen) inférieur à 2 ms est le défi technique suprême de cette architecture. Les approches basées sur l'intelligence artificielle générative ou sur des algorithmes de type DIS (Dense Inverse Search) dense et complet s'avèrent beaucoup trop lourdes pour un utilitaire léger.1 Le paradigme le plus efficient repose sur l'estimation de mouvement par "Block Matching" hiérarchique, couplée à des primitives d'accélération matérielle.

Accélération Matérielle : L'Intrinsèque msad4
Évaluer cette équation itérativement pixel par pixel détruirait les performances. Heureusement, les spécifications DirectX (Shader Model 5.0+) fournissent une instruction intrinsèque spécifiquement conçue pour l'encodage vidéo et la recherche de mouvement : msad4.4
L'instruction msad4 compare simultanément une valeur de référence codée sur 4 octets avec une valeur source de 8 octets, et accumule un vecteur de 4 sommes absolues en un seul cycle d'horloge au niveau de l'ALU.22 Cela permet de traiter une ligne entière d'un bloc de    pixels en une seule instruction HLSL.
Le processus global de recherche s'architecture autour d'une pyramide hiérarchique. Au lieu d'effectuer une recherche exhaustive coûteuse sur l'image pleine résolution, l'image est sous-échantillonnée en plusieurs niveaux (par exemple, résolution divisée par 4, puis par 2, puis résolution native).1 Le vecteur de mouvement est d'abord estimé grossièrement sur le niveau le plus bas de la pyramide, puis propagé et affiné au niveau supérieur, limitant drastiquement l'espace de recherche (Search Window) à chaque itération.
Logique d'implémentation HLSL pour le raffinement via msad4 :






High-level shader language
// Fonction de raffinement du vecteur de mouvement au sein d'une fenêtre de recherche
float2 RefineMotionVector(uint2 blockPos, float2 predictedVector) {
   float minSAD = 999999.0f;
   float2 bestVector = predictedVector;
   
   // Chargement du bloc de luminance 4x4 courant via conversion en uint
   // Optimisation : stockage dans les registres locaux du thread
   uint4 currentBlockLuma = LoadBlock4x4_Uint(blockPos, CurrentFrameLuma);
   
   // Itération circonscrite sur la fenêtre de recherche (ex: grille de -4 à +4 pixels)
   [unroll]
   for(int dy = -4; dy <= 4; dy++) {
       for(int dx = -4; dx <= 4; dx++) {
           float2 candidateVector = predictedVector + float2(dx, dy);
           
           // Chargement du bloc candidat dans la trame précédente
           uint4 searchBlockLuma = LoadBlock4x4_Uint(blockPos + candidateVector, PreviousFrameLuma);
           
           // Accélération matérielle : Calcul vectoriel du SAD en 2 instructions
           uint4 sadVector = msad4(currentBlockLuma.x, searchBlockLuma.xy);
           sadVector += msad4(currentBlockLuma.y, searchBlockLuma.yz); 
           // Répétition pour les canaux z et w omise pour la concision
           
           // Somme horizontale finale
           float currentSAD = sadVector.x + sadVector.y + sadVector.z + sadVector.w;
           
           if(currentSAD < minSAD) {
               minSAD = currentSAD;
               bestVector = candidateVector;
           }
       }
   }
   return bestVector;
}

Interpolation Temporelle et Suppression des Artefacts (Ghosting)
Une fois le champ vectoriel (Motion Vector Field) généré et stocké dans une texture de format DXGI_FORMAT_R16G16_FLOAT, l'algorithme procède à l'interpolation.21 La trame intermédiaire est synthétisée en déplaçant les pixels de    vers l'avant selon une demi-magnitude vectorielle (  ) et les pixels de    vers l'arrière selon l'inverse du vecteur.1 Un mélange bilatéral (Bilateral Blending) fusionne ensuite les deux projections.
Toutefois, ce processus mathématique pur échoue systématiquement lors des occlusions (un objet se déplace et révèle un arrière-plan précédemment caché). Pousser des pixels dans une zone de disocclusion génère un étirement visuel indésirable connu sous le nom de "Ghosting". La résilience de l'algorithme repose sur le masque de disocclusion (Disocclusion Mask).21 Lors du calcul du SAD, si la valeur d'erreur minimale du meilleur vecteur excède un seuil de confiance strict, le shader identifie la zone comme une disocclusion. Le mélange vectoriel est alors annulé pour ces pixels spécifiques, et l'algorithme effectue un repli analytique (Fallback) en copiant simplement le pixel source le plus proche ou en effectuant un fondu enchaîné statique.
Gestion de la Mémoire et Règles Strictes VRAM (docs/04_memory_management.md)
Une application dont la vocation est l'optimisation des performances ne doit sous aucun prétexte devenir elle-même une source de ralentissement système. La fragmentation insidieuse de la mémoire graphique, le forçage des processus de ramasse-miettes (Garbage Collection) du pilote d'affichage, et les pics asynchrones d'utilisation de la VRAM (Memory Spikes) sont les causes profondes du micro-stuttering dans les utilitaires mal conçus.
Allocation Statique Intégrale (Pre-Allocation)
La règle architecturale primordiale est formelle : toute allocation dynamique de ressources est strictement prohibée dans la boucle principale (Main Loop). Les appels aux constructeurs d'API tels que CreateTexture2D, CreateBuffer, ainsi que l'utilisation des opérateurs d'allocation dynamique du langage hôte (new, malloc, Box::new en Rust) ne doivent figurer que dans la routine d'initialisation (Init()).
Le graphe des ressources graphiques doit être calculé et instancié statiquement. Le budget mémoire VRAM typique pour ce pipeline est d'environ 60 à 80 Mo, décomposé comme suit :
1. Texture Staging / Conversion : Utilisée pour l'extraction de luminance (NV12 ou RGBA vers format monochrome scalaire R8_UNORM).
2. Pyramide de Luminance (Mipmaps manuels) : Pré-allocation de 3 à 4 textures représentant les résolutions décimées (1/2, 1/4, 1/8) nécessaires à l'Optical Flow hiérarchique.1
3. Champ Vectoriel (Motion Vectors) : Texture de format DXGI_FORMAT_R16G16_FLOAT encapsulant la vélocité directionnelle sur les axes X et Y.
4. Cibles d'Interpolation (Backbuffers) : 2 textures de pleine résolution pour stocker la trame native upscalée et la trame synthétique générée.
Ce graphe statique garantit que le système d'exploitation n'aura jamais à paginer la mémoire vidéo de l'utilitaire vers la mémoire système via le bus PCI-Express, protégeant ainsi l'intégrité temporelle du pipeline de rendu du jeu ciblé.
Résolution Déterministe des Aléas de Pipeline (Pipeline Hazards)
Sous DirectX 11, et de manière encore plus explicite sous DirectX 12 et Vulkan, lier simultanément une même ressource mémoire en tant que cible de rendu en écriture (Unordered Access View - UAV) et en tant que ressource en lecture (Shader Resource View - SRV) provoque une collision d'état, communément appelée "Pipeline Hazard".14
Face à ce conflit, le pilote graphique réagit défensivement en injectant des barrières de synchronisation implicites et des vidages de cache (Cache Flushes) qui détruisent le parallélisme d'exécution du processeur graphique. Pour maintenir un surcoût d'exécution nul, l'architecture C++/Rust doit procéder à une déliaison (Unbinding) explicite des vues avant toute mutation d'état :






C++
// 1. Déliaison explicite et agressive des SRV (Lectures)
ID3D11ShaderResourceView* nullSRVs = { nullptr, nullptr, nullptr, nullptr };
// Annule les liens sur les slots 0 à 3 du pipeline Compute
d3dContext->CSSetShaderResources(0, 4, nullSRVs);

// 2. Liaison sécurisée de la cible en écriture (UAV)
// La VRAM est maintenant prête à recevoir les calculs sans déclencher de Hazard de pilote
d3dContext->CSSetUnorderedAccessViews(0, 1, &targetUAV, nullptr);

// 3. Exécution asynchrone du groupe de travail (Dispatch)
d3dContext->Dispatch(threadGroupsX, threadGroupsY, 1);

Cette hygiène de gestion d'état s'étend au suivi des drapeaux de liaison (Bind Flags).14 Les textures ne doivent être créées qu'avec les combinaisons strictement nécessaires (généralement D3D11_BIND_SHADER_RESOURCE | D3D11_BIND_UNORDERED_ACCESS).
UI, Overlay et Compositing Transparent (docs/05_ui_and_overlay.md)
L'affichage de la trame finale (upscalée ou générée) par-dessus la fenêtre du jeu s'appuie sur le concept de fenêtre sans bordure (Borderless Overlay). Les implémentations classiques, historiquement basées sur l'API GDI (UpdateLayeredWindow) ou sur des Swapchains DXGI traditionnels modifiés par des attributs alpha, forcent le système d'exploitation à effectuer des copies de surfaces redondantes entre le CPU et le GPU, et échouent souvent à laisser passer les interactions de la souris (Click-Through) de manière fiable, ruinant l'expérience utilisateur.
Le Paradigme DirectComposition (DComp)
L'architecture de pointe sous les systèmes Windows modernes (10 et 11) repose sur le moteur d'interface DirectComposition (DComp).24 DComp court-circuite le pipeline Win32 standard. Il permet à l'application de soumettre une chaîne de permutation DXGI intégrant un canal alpha directement au Desktop Window Manager (DWM). Le DWM superpose alors cette surface directement au niveau de la couche de composition matérielle du GPU, à l'instar d'une texture additionnelle collée sur l'écran, annihilant tout délai d'affichage.24
Pour instancier ce paradigme, la séquence de création de la fenêtre d'overlay et du contexte graphique est soumise à des règles strictes.
1. Propriétés de la Fenêtre Win32 :
La fenêtre hôte (HWND) doit être déclarée avec une matrice de styles étendus spécifiques :
* WS_EX_LAYERED : Informe l'OS que la fenêtre possède des attributs de transparence.
* WS_EX_TRANSPARENT : Assure la perméabilité totale aux événements périphériques (souris/clavier).28 Le clic traverse l'overlay et atteint le jeu situé en dessous.
* WS_EX_TOPMOST : Maintient l'élévation spatiale au-dessus de toutes les autres fenêtres (Z-Order absolu).
* WS_EX_NOREDIRECTIONBITMAP : La directive critique. Ce style ordonne au sous-système Windows de ne pas allouer le buffer de redirection habituel en mémoire système (RAM), économisant des mégaoctets de mémoire et prévenant les copies parasites de rafraîchissement.29 La fenêtre devient une simple coquille logique vide.
2. Architecture de la Chaîne de Permutation DComp : Le Swapchain D3D11 ne doit pas être lié conventionnellement au handle de la fenêtre via CreateSwapChainForHwnd. Il doit être généré spécifiquement pour la composition via CreateSwapChainForComposition.25






C++
// 1. Initialisation de la chaîne de permutation asynchrone DComp
DXGI_SWAP_CHAIN_DESC1 swapChainDesc = {};
swapChainDesc.Format = DXGI_FORMAT_B8G8R8A8_UNORM;
swapChainDesc.Stereo = FALSE;
swapChainDesc.SampleDesc.Count = 1;
swapChainDesc.SampleDesc.Quality = 0;
swapChainDesc.BufferUsage = DXGI_USAGE_RENDER_TARGET_OUTPUT;
swapChainDesc.BufferCount = 2; // Double buffering
// Mode SwapEffect FLIP crucial pour l'efficience du DWM
swapChainDesc.SwapEffect = DXGI_SWAP_EFFECT_FLIP_SEQUENTIAL;
// Premultiplied Alpha pour le blending natif du DWM
swapChainDesc.AlphaMode = DXGI_ALPHA_MODE_PREMULTIPLIED; 

winrt::com_ptr<IDXGISwapChain1> compositionSwapChain;
dxgiFactory->CreateSwapChainForComposition(
   d3dDevice.get(),
   &swapChainDesc,
   nullptr,
   compositionSwapChain.put()
);

// 2. Construction de l'Arbre Visuel DirectComposition (Visual Tree)
winrt::com_ptr<IDCompositionDevice> dcompDevice;

Le recours à l'arbre visuel DirectComposition garantit que la couche applicative est visuellement indiscernable et temporellement arrimée au rafraîchissement vertical de l'écran, n'introduisant littéralement aucune trame de délai supplémentaire à la présentation (Input Lag).24
Gestion des Threads, Frame Pacing et Haute Résolution Temporelle
La génération de trames intermédiaires introduit une problématique majeure souvent sous-estimée : la synchronisation rythmique de l'affichage, connue sous le nom de Frame Pacing. Supposons qu'un moteur de jeu produise des trames de manière irrégulière autour de 30 FPS. L'objectif de l'utilitaire est de générer des trames interpolées pour atteindre un affichage fluide à 60 FPS.
La trame générée    ne doit pas être affichée dès que son calcul est terminé. Elle doit être retenue et présentée exactement à mi-chemin temporel entre la trame précédente et la trame suivante (soit idéalement à    ms après la première trame dans notre scénario). Un écart de présentation de seulement 2 ou 3 millisecondes provoque un déséquilibre rythmique, induisant un "micro-stuttering" sévère.21 L'œil humain est extrêmement sensible à cette asymétrie temporelle, annulant les bénéfices de la fluidité artificielle.
Le Défaut Fondamental de la Résolution des Timers Windows
En C++ standard, les fonctions de délai (telles que std::this_thread::sleep_for() ou l'API Win32 classique Sleep()) délèguent l'ordonnancement au gestionnaire de tâches du noyau Windows. Historiquement, l'intervalle minimal de réveil de l'horloge système (Timer Resolution) est verrouillé à environ    millisecondes.36
Pour obtenir une précision supérieure, les développeurs manipulaient historiquement la granularité du noyau via l'appel API multimédia timeBeginPeriod(1) pour descendre à    ms de résolution. Cependant, afin de préserver l'autonomie énergétique des processeurs modernes, Microsoft a altéré en profondeur le comportement de cette API depuis Windows 10 (version 2004).36 Invoquer timeBeginPeriod n'offre plus aucune garantie déterministe sur le réveil d'un thread. Par conséquent, demander un Sleep(8) (attente de 8 ms pour caler une trame intermédiaire) peut résulter en un réveil aléatoire entre 8 et 15 ms, détruisant instantanément le Frame Pacing de l'utilitaire.
L'Architecture Déterministe : CREATE_WAITABLE_TIMER_HIGH_RESOLUTION
L'architecture contemporaine et robuste pour un Frame Pacing parfait repose sur l'API asynchrone des Waitable Timers introduite secrètement dans Windows 10 (1803) et documentée publiquement par la suite.36 L'astuce fondamentale réside dans l'exploitation du drapeau système d'initialisation CREATE_WAITABLE_TIMER_HIGH_RESOLUTION.37
Ce marqueur instruit le noyau NT de contourner l'horloge de coalescence standard et de s'aligner sur des compteurs matériels précis, autorisant la mise en sommeil et le réveil d'un thread avec une précision s'évaluant en centaines de nanosecondes (soit    ms de précision), ce qui est vital pour un placement chirurgical de la trame vidéo.37

// 1. Initialisation isolée du timer asynchrone haute résolution
HANDLE hHighResTimer = CreateWaitableTimerExW(
   NULL, 
   NULL, 
   CREATE_WAITABLE_TIMER_HIGH_RESOLUTION, 
   TIMER_ALL_ACCESS
);

// Variables de profilage (Trace ETW/Tracy)
LARGE_INTEGER performanceFrequency, lastFrameTime;
QueryPerformanceFrequency(&performanceFrequency);

// 2. Boucle d'exécution asynchrone principale
void FramePacingRenderLoop() {
   while(IsRunning) {
       // A. Capture Zero-Copy de la trame native T
       auto frame = CaptureLatestFrameWGC();
       
       // B. Exécution asynchrone du pipeline de Compute Shaders (Flow + Upscale)
       // Coût architectural contraint : < 2.0 ms
       DispatchComputeShaders();
       
       // C. Soumission immédiate de la trame originale (T) au Swapchain DComp
       PresentFrame(OriginalUpscaledFrame);
       
       // D. Calcul prédictif du délai pour atteindre le centre temporel (T + 0.5)
       // Estimation dynamique de la cadence du jeu via QueryPerformanceCounter
       double targetFrameTimeMs = CalculateDynamicFrameTime(); 
       
       // Configuration de l'intervalle de réveil (exprimé en pas de 100 nanosecondes)
       // La valeur négative spécifie un délai relatif
       LARGE_INTEGER dueTime;
       dueTime.QuadPart = -static_cast<LONGLONG>((targetFrameTimeMs * 10000.0) / 2.0); 
       
       // E. Mise en sommeil déterministe (Le thread relâche totalement le processeur)
       SetWaitableTimerEx(hHighResTimer, &dueTime, 0, NULL, NULL, NULL, 0);
       
       // F. Blocage du thread jusqu'à la notification exacte du timer NT
       WaitForSingleObject(hHighResTimer, INFINITE);
       
       // G. Soumission au point de synchronisation parfait de la trame interpolée (T+0.5)
       PresentFrame(GeneratedInterpolatedFrame);
   }
}

L'application combinée de CREATE_WAITABLE_TIMER_HIGH_RESOLUTION et de la chaîne de permutation DirectComposition garantit un espacement régulier entre les trames réelles et interpolées. L'Input Lag ajouté au jeu est mathématiquement limité à la moitié du frametime natif (ex: +16 ms si le jeu tourne à 30 FPS, puisque la trame    est affichée sans aucun délai de traitement additionnel autre que les ~1 ms d'exécution du shader, la trame    étant différée artificiellement). C'est ainsi que l'on surpasse l'ergonomie des utilitaires de la concurrence.
